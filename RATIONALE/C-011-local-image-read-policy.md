# C-011 本地图片读取口径与聊天界面对齐

日期: 2026-11-17

#### 上下文

C-010 把「嵌入原图」扩展到消息正文里的 Markdown 本地图片，同时把读取通道登记成「受宿主的权限与沙箱策略约束」。累计审计（T-016）核对宿主实现后确认这句不成立：宿主的 fs-sandbox 只约束写入，读取、列目录与元数据不受限制（宿主的文件系统说明写明读取与本地后端完全一致）；聊天界面的文件读取服务同样不施加工作区围栏，但会用 `lstat` 拒绝最终符号链接。C-010 这句表述同时写进了 PRD 的 AC-07、SOLUTION 与 DOMAIN，承诺比实现强，审计按 blocking 记录。

#### 决策

嵌入范围不变，读取口径改为与聊天界面一致：本地图片经宿主文件服务 `ctx.fs` 读取，读取权限等同宿主进程，宿主沙箱只约束写入；任意本地绝对路径可读，相对路径按会话工作区解析；读取前用 `lstat` 判定类型并拒绝最终符号链接；只接受常见图片扩展名且字节嗅探为真图片，读取上限沿用宿主附件图片准入上限；http、https 远程地址不抓取，读取失败回退 `[图片: alt]` 文字。东家 2026-11-17 在三个选项中选 A（与聊天界面对齐）。

#### 被否方案及原因

- **把读取范围限制在会话工作区与系统临时目录**（东家选项 B）：隔离更强，但与聊天界面不一致——同一条消息在聊天里看得见图，导出只给占位文字；截图常放在工作区外，割裂的代价大于隔离收益。
- **维持「沙箱约束读取」的表述、不改实现**（东家选项 C）：承诺无法兑现，审计 blocking 无法消除；把不成立的隔离写成产品承诺，比不承诺更危险。
- **在插件里直接调用 Node `fs`**：绕过宿主文件服务，等于自建一条不受宿主观察的读取通道，与 C-010 的否决理由相同。
- **在拒绝符号链接之外再做 realpath 包含检查**：聊天界面没有这条围栏，加上会让两侧行为分叉；最终符号链接拒绝已覆盖「路径指向意外文件」的主要风险。
