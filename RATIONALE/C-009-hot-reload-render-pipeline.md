# C-009 用内容哈希热加载渲染管线，并把页面样式抽成数据文件

日期: 2026-11-17

#### 上下文

本插件迭代频繁，版式与渲染逻辑改动占多数；但宿主侧模块在 `dsh web` 启动时 import，进程内没有文件监听，任何宿主代码改动都要重启实例。主实例同时跑多个会话，重启会打断这些会话，东家判定不可接受，要求把“改完即生效”覆盖到渲染层。页面样式此前是 `render.mjs` 里的 `PAGE_STYLE` 常量，一次版式调整也要重启。

#### 决策

渲染层整体热加载：宿主在导出时按源码内容判断版本，内容变化就加载新代码；页面样式抽成独立的数据文件，由导出时读取。这样改渲染逻辑、Markdown 规则与样式都在下一次导出生效，不需要重启宿主；宿主装配、路由与配置仍在启动时固定。具体加载机制、缓存键与失败语义由 SOLUTION 承载。

#### 被否方案及原因

- **每次改完手动重启宿主**: 改动为零，但正是要解决的问题；主实例上的并行会话会被打断。
- **只做样式数据化**: 能覆盖版式调整，逻辑改动（Markdown 规则、折叠、图片处理）仍要重启，达不到“最大程度减少重启”。
- **子进程渲染**: 每次导出起一个 Node 子进程，天然拿到最新代码且无需模块缓存技巧；代价是新增进程协议、图片字节与事件要跨进程序列化、错误映射多一层，还改变导出编排的现有边界。进程内生成模块能达到同样的新鲜度，改动面更小。
- **运行时用 `new Function` 直接求值拼接源码**: 同样能绕开模块缓存，但不保留真实模块语义与文件路径，堆栈与调试体验更差，也被安全审查视为 eval 面。
- **引入 esbuild 等打包器生成管线产物**: 构建产物与缓存破坏更标准，但破坏“不引入运行时/构建依赖”的现有约束，且需要额外构建命令或 watch 进程。
- **依赖 DSH 上游提供宿主热重载**: 当前 DSH 没有宿主侧文件监听或插件 reload API，插件市场对已挂载插件的更新也要求重启；本仓库无法单方实现。
- **把 HTML 生成挪到浏览器半区**: 天生可热更新，但 PDF 要由用户浏览器打印，预览/下载同字节与文件名契约都要改，等于推翻既有需求。

#### 影响面

会话导出 · 渲染管线与页面样式（T-013）
