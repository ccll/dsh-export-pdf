# C-008 用无依赖的安全 Markdown 子集渲染 PDF 正文

日期: 2026-11-17

#### 上下文

PDF 正文此前把消息文本整体转义后放进 `white-space: pre-wrap` 容器，标题、列表、代码块、表格和行内强调都保留原始标记；东家要求所有 Markdown 内容显示渲染后的格式。正文来自不可信的会话日志，既要在 PDF 中排版，又不能执行 HTML、抓取外部图片或打开危险协议链接。

#### 决策

采用无运行时依赖的安全 Markdown 子集：块级覆盖标题、列表、引用、围栏代码、表格、分隔线与段落，行内覆盖加粗、斜体、删除线、行内代码、链接与图片占位，输出受控 HTML。原始 HTML 始终按文本转义；链接只允许 http、https、mailto；Markdown 图片语法只呈现占位文字，不读取 URL。未匹配的标记按普通文本保留，保证无 Markdown 的消息仍可读。具体模块落点与实现结构由 SOLUTION 承载。

#### 被否方案及原因

- **引入 `marked` 等运行时依赖**: GFM 覆盖更完整，但破坏项目“不引入运行时 npm 依赖”的约束，且原始 HTML、链接协议与图片地址仍需额外的安全渲染器；为当前消息格式引入包体与供应链面不划算。
- **保留原始 Markdown 文本**: 改动最小，但直接违背东家诉求，长会话中的标题、列表和代码块难以阅读。
- **只处理行内强调**: 能改善少量文本，但标题、列表、代码块与表格仍保留标记，不能满足“所有 Markdown 内容”。
- **在浏览器端先渲染再打印**: PDF 由宿主侧 Chrome 打印，客户端渲染器无法复用到导出 HTML；且会引入双份渲染逻辑。
